# Phase 1 — Initial capability matrix and product-contract inventory

**Method and scope.** Static inspection of repository source, tracked documentation, and tests, excluding `_review/` except the supplied `codemap.md`. This is an initial inventory, not a runtime enumeration. `absent` means no implementation/registration was found in the inspected application sources and packaging metadata; it does not infer that every HTTP operation should also exist as a CLI, MCP tool, SDK, job, or webhook.

Status vocabulary: **present** = concrete implementation found; **partial** = only a subset/indirect form exists; **absent** = no surface implementation found; **unknown** = static evidence cannot establish it.

## Parity conclusion for Phase 1 handoff

The product’s strong, repeated contract is **HTTP-first**: all business mutations and machine reads are HTTP endpoints; browser UI is intentionally limited to landing/read/unlock/history/diff rendering, while Swagger provides generic interactive access. Documentation explicitly addresses agents through an HTTP manifest and a served SKILL.md, not through MCP. No discovered public contract promises that management, publishing, moderation, or versioning must also be exposed through a CLI, MCP tools/resources/prompts, generated SDK, jobs, or webhooks. The one static registry discrepancy to retain for subsequent parity review is that `GET /health/headers` is registered and represented in generated OpenAPI metadata but omitted from the `context()` endpoint list and the public prose docs.
